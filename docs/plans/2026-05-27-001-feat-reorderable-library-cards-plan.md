# feat: Reorderable lifecycle cards on Library View

## Summary

Add a per-library "Arrange Layout" mode that lets users reorder the five main cards on the Library View detail page (Files, Status, Agent Tool, Test, Deploy) using a drag-and-drop interaction modeled on iOS home-screen jiggle. Entry is moved from a `[Edit]` link to a settings-icon dropdown that exposes Edit Library Details, Arrange Layout, and (placeholder) New Version. Order is persisted per library to the JSON-backed Express store.

## Problem Frame

The Library View page currently renders four lifecycle cards in a fixed order beneath a Files card. Users have asked for a way to reorganize the cards to match how they think about a library — e.g., promote Deploy if a library is in production, push Test up while iterating. This is a UX prototype goal — exploring whether per-library card arrangement makes the page feel more like a workspace than a fixed dashboard.

The change is scoped to the existing-library view (`LibraryView.jsx`). The create-new flow (`LibraryDetail.jsx`) is out of scope.

## Scope Boundaries

### In scope

- `src/components/LibraryView/LibraryView.jsx` — full reorder flow + toolbar dropdown
- All five cards: Files, Status, Agent Tool, Test, Deploy
- Per-library backend persistence via `PUT /api/libraries/:id` with new `cardOrder` field
- New jiggle CSS animation (Status / Agent Tool / Test / Deploy only)
- Reduced-motion support
- Esc-to-cancel
- Demo-library parity: reorder works locally for the session but no PUT (mirrors existing `persistLibraryPatch` behavior)

### Out of scope (deferred)

- `LibraryDetail.jsx` (create-new flow) — no reorder
- Sidebar / library-list reorder
- Hide / show / pin individual cards
- Keyboard-only drag accessibility beyond what dnd-kit provides by default
- "New Version" handler — menu item stub only, no behavior

---

## High-Level Technical Design

A single `SortableContext` wraps an array of card ids `['files', 'status', 'agentTool', 'test', 'deploy']` and renders each card via a small `<SortableCard>` component that applies `useSortable` transforms. The visible card order derives from `library.cardOrder` (falling back to the default array). Arrange mode is a single boolean state in `LibraryView`; entering it snapshots the current order, switches the footer, and toggles a CSS class that animates the four lifecycle cards.

```
arrangeMode: false → click "Arrange Layout" in settings dropdown
arrangeMode: true  → snapshot order, footer = [Cancel | Done]
                     cards: jiggle (4 of 5), pointer-blocking overlay over each card body,
                            dnd-kit listeners on the entire card surface
                     Done  → PUT cardOrder (skip if isDemo) → arrangeMode = false
                     Cancel/Esc → restore snapshot → arrangeMode = false
```

This is directional guidance for review, not implementation specification.

### U2. Add jiggle CSS animation + reduced-motion fallback

**Goal:** Provide an `.arrange-jiggle` class that produces a gentle ±0.6° rotation at ~5Hz, with a static fallback for `prefers-reduced-motion`.

**Files:**
- `src/index.css` (append `@keyframes arrange-jiggle`, `.arrange-jiggle`, optional `.arrange-jiggle-delay-{1,2,3,4}` helpers, and a `@media (prefers-reduced-motion: reduce)` block that disables rotation and applies a faint inset border / ring instead)

**Approach:**
- Keyframes: `0% { transform: rotate(-0.6deg); } 50% { transform: rotate(0.6deg); } 100% { transform: rotate(-0.6deg); }`
- Animation: ~0.18s linear infinite (≈5Hz cycle).
- Use `animation-delay` variants (e.g., `-40ms`, `-90ms`, `-130ms`) so cards desync.
- Reduced motion: replace animation with a static `box-shadow: inset 0 0 0 1px <muted-foreground>` + `cursor: grab`.
- A child rule disables the animation when an ancestor has `data-dragging="true"` (the picked card stops jiggling).

**Verification:** Toggling `.arrange-jiggle` on a card in DevTools shows the rotation; flipping `prefers-reduced-motion` in DevTools removes the rotation but keeps a clear "lifted" affordance.

### U3. Server: accept `cardOrder` on PUT and validate

**Goal:** Allow `cardOrder` to round-trip through `PUT /api/libraries/:id` without accepting arbitrary ids.

**Files:**
- `server/routes/libraries.js`
- `server/store.js` (only if updateLibrary needs sanitization; expected unchanged)

**Approach:**
- The current PUT handler simply forwards `req.body` to `updateLibrary`. Introduce a small whitelist before forwarding.
- Whitelist allowed top-level fields explicitly so `cardOrder` is added to a known set rather than the route silently accepting whatever the client sends.
- Allowed ids constant: `['files', 'status', 'agentTool', 'test', 'deploy']`. Validate `cardOrder`:
  - Must be an array.
  - Every entry must be one of the allowed ids.
  - No duplicates.
  - If invalid, drop it from the patch (do NOT 400 — keep the demo robust).
- Existing behavior for other fields (`libraryName`, `apiName`, `dataSpace`, `description`, `useAI`, `status`, `files`, `testCases`, `deployment`, `cardOrder`, `updatedAt`) preserved.

**Test scenarios:**
- PUT with valid `cardOrder` → response includes the new order; `data.json` updated.
- PUT with `cardOrder` containing an unknown id → patch applied to other fields, `cardOrder` dropped silently.
- PUT with `cardOrder` containing duplicates → dropped silently.
- PUT with `cardOrder: "not-an-array"` → dropped silently.
- PUT without `cardOrder` → existing fields untouched (regression check).

**Verification:** `curl -X PUT` with each shape above behaves as described.

### U4. Sortable card primitive

**Goal:** A small wrapper that turns any of the five cards into a draggable item, with an overlay that blocks normal interaction during arrange mode.

**Files:**
- `src/components/LibraryView/SortableCard.jsx` (new)

**Approach:**
- Component signature: `<SortableCard id={cardId} arranging={boolean} jiggle={boolean}>{children}</SortableCard>`
- Uses `useSortable({ id })` from `@dnd-kit/sortable` and `CSS.Transform.toString` from `@dnd-kit/utilities`.
- Outer wrapper applies:
  - `transform`, `transition` from dnd-kit
  - `data-dragging={isDragging}` (used by jiggle CSS to suppress animation on the picked card)
  - `className` includes `arrange-jiggle` only when `arranging && jiggle && !isDragging`
  - Lifted state when `isDragging`: `scale(1.02)` + stronger `box-shadow` (Tailwind utility classes are fine)
  - `cursor: grab` when `arranging`, `grabbing` when `isDragging`
- When `arranging` is true, render an absolutely-positioned transparent overlay (`position: absolute; inset: 0; z-index: 1`) over the card content with the dnd-kit listeners attached. The overlay blocks clicks from reaching internal `Collapsible` triggers, expand chevrons, etc., while still allowing drag to start. When `arranging` is false, the overlay is unmounted and listeners are detached.
- The card body remains at a lower z-index so the overlay sits above it visually but the card is still rendered (for layout and content updates from the pipeline).

**Test scenarios:**
- (manual) Render with `arranging=false`: clicking inner Collapsible header expands/collapses normally.
- (manual) Render with `arranging=true`: clicking inner Collapsible header does nothing; pressing-and-dragging from anywhere on the card initiates drag.
- (manual) `arranging=true, jiggle=true`: card jiggles when not being dragged, stops jiggling while dragging.
- (manual) `arranging=true, jiggle=false`: card does not jiggle but can still be dragged (Files behavior).

**Verification:** Drop into a throwaway page or rely on integration in U6.

### U6. Arrange-mode state, sortable list integration, and persistence

**Goal:** Wire the cards into a single dnd-kit sortable list, manage arrange mode, persist new order on Done.

**Files:**
- `src/components/LibraryView/LibraryView.jsx`

**Approach:**

State and helpers (added to `LibraryView`):
- `const [arrangeMode, setArrangeMode] = useState(false)`
- `const [cardOrder, setCardOrder] = useState(() => library.cardOrder ?? DEFAULT_CARD_ORDER)`
- `const arrangeSnapshotRef = useRef(null)` — holds the order at the moment arrange mode was entered.
- `const DEFAULT_CARD_ORDER = ['files', 'status', 'agentTool', 'test', 'deploy']`
- `const ALLOWED_IDS = new Set(DEFAULT_CARD_ORDER)`
- Sanitizer: when reading from `library.cardOrder`, drop unknown ids and append any missing default ids in their default position. This protects against stale stored orders if the set of cards ever changes.

Lifecycle:
- When entering arrange mode (settings menu → Arrange Layout):
  - `arrangeSnapshotRef.current = cardOrder`
  - `setArrangeMode(true)`
- Done:
  - If `!library.isDemo`: call `persistLibraryPatch({ cardOrder })` (existing helper handles PUT and `onLibraryUpdate`).
  - `setArrangeMode(false)`
- Cancel / Esc:
  - `setCardOrder(arrangeSnapshotRef.current)`
  - `setArrangeMode(false)`
- Esc handler: `useEffect` that adds a `keydown` listener while `arrangeMode` is true; calls Cancel path on Escape.

Render:
- Wrap the entire card region (currently five sibling components inside the scrollable region at `LibraryView.jsx:728–968`) in:
  ```
  <DndContext onDragEnd={handleDragEnd} sensors={sensors}>
    <SortableContext items={cardOrder} strategy={verticalListSortingStrategy}>
      {cardOrder.map(renderCard)}
    </SortableContext>
  </DndContext>
  ```
- `renderCard(id)` is a switch on the id that returns the existing JSX for that card wrapped in `<SortableCard id={id} arranging={arrangeMode} jiggle={id !== 'files'}>`.
- `handleDragEnd({ active, over })`: standard `arrayMove` of `cardOrder`.
- Sensors: `useSensors(useSensor(PointerSensor, { activationConstraint: { distance: 4 } }), useSensor(KeyboardSensor, { coordinateGetter: sortableKeyboardCoordinates }))`. The 4px distance avoids accidental drags from clicks.

Footer swap (`LibraryView.jsx:971–998`):
- When `arrangeMode` is true, replace the entire footer button group with:
  - `Cancel` → cancel path
  - `Done` → done path (always enabled)
- Remove visibility of Save / Remove Files buttons in this mode (early-return the existing branch when `arrangeMode` is true). The Cancel button click handler distinguishes its three contexts: edit metadata (existing), normal (existing), arrange (new).

Pipeline updates while arranging:
- `cardOrder` is independent of the data flowing into each card. SSE updates, `setPipelineSteps`, `setAgentToolReady`, etc., continue to fire and re-render the cards. Confirm no `useEffect` deps depend on arrange mode for pipeline machinery.

Auto-expand signals (`statusCardKey`, `agentToolAutoExpandSignal`, `testCardAutoExpandSignal`, `deployCardAutoExpandSignal`):
- These are state-driven and key-based. After a reorder, React reconciles by `id` from the SortableContext; the underlying card components keep their identity because we render them in a `useMemo`-stable wrapper indexed by id. No additional work expected — call out as a verification step.

**Test scenarios (manual):**
- Enter arrange mode on a fresh non-demo library → all four lifecycle cards jiggle with subtly different timing; Files does not.
- Drag Files to bottom → other cards reflow with smooth spring; click Done → `data.json` shows `cardOrder: ['status','agentTool','test','deploy','files']`; refresh page → order persists.
- Demo library (`isDemo: true`) → reorder works visually; Done does not PUT (network tab quiet); refresh resets to default (expected).
- Cancel button → order reverts to snapshot; Esc → same behavior.
- Pipeline running while arranging: trigger an upload (or use an active demo) → arrange mode and confirm Status card text/percentage continues to update; exit arrange mode and confirm card content matches latest pipeline state.
- `prefers-reduced-motion: reduce` (DevTools rendering tab) → no jiggle; cards have a static lifted indicator; drag still works.
- Auto-expand: after reordering, complete a pipeline step that should expand Agent Tool / Test / Deploy → cards still auto-expand correctly.

**Verification:**
- Compiles with `npm run build`.
- Dev server hot-reloads cleanly.
- All test scenarios pass.

## Risks & Open Questions

- **Pointer overlay vs. drag handle.** We chose a full-card overlay during arrange mode rather than a dedicated handle. This means the *only* way to interact with a card while arranging is to drag it. Verified intentional by brainstorm.
- **Files card height.** The Files card can be tall (long file lists). Lifting a tall card with `scale(1.02)` may look heavy. If it looks bad in practice, the lift can be reduced to `scale(1.01)` or replaced with shadow-only — small CSS tweak, no plan implications.
- **Auto-expand signals after reorder.** Belt-and-suspenders: if React reconciliation drops state across reorders, we may need to key the cards by id (already implicit through SortableContext). Listed as a verification step.
